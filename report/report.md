### 2.3 关于内核装载方式的环境差异

实验框架 `Makefile` 的 `qemu` 目标默认使用以下参数装载内核：

```text
-machine virt -nographic -bios default -device loader,file=bin/ucore.img,addr=0x80200000
```

该写法在 **QEMU 4.1.1** 环境下可以正常工作（张旭的环境），因为彼时 `virt` 机器的默认固件是 `fw_jump` 形态的 OpenSBI，其跳转目标地址 `0x80200000` 是固件内部写死的。

但在**较新版本的 QEMU**（另两位成员的环境）下，默认固件改为 `fw_dynamic` 形态：下一阶段的入口地址不再写死，而是由 QEMU 通过固件信息结构动态传入，**而这个结构只有在使用 `-kernel` 参数时才会被填写**。`-device loader` 仅负责把镜像字节写入内存，不设置跳转地址，因此 OpenSBI 启动后报告的下一阶段入口为 0，控制权无法移交，表现为只打印固件横幅而不见内核输出。

解决办法是改用 `-kernel` 装载。本组采用的方式为：

```bash
make qemu  QEMU='qemu-system-riscv64 -kernel bin/ucore.img'
make debug QEMU='qemu-system-riscv64 -kernel bin/ucore.img'
```

`Makefile` 开头的 `ifndef QEMU` 使该变量可从命令行覆盖，因此**无需修改框架提供的任何文件**即可在新版 QEMU 上运行。经实测，修正后 OpenSBI 正确报告：

```text
Domain0 Next Address      : 0x0000000080200000
Domain0 Next Mode         : S-mode
```

补充说明：`-kernel` 参数对 ELF 文件（`bin/kernel`）和裸二进制镜像（`bin/ucore.img`）均可接受，两者实测都能正常启动，因为 QEMU 自身能够解析 ELF 程序头并按段装入。

## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

Lab1 的目标是构建并运行一个能够完成格式化输出的最小 RISC-V 操作系统内核。本实验尚未实现进程调度、虚拟内存管理和文件系统等功能，主要解决内核的编译与装载、启动入口与内存布局、基本运行环境初始化，以及通过 OpenSBI 完成控制台输出等基础问题。

本章按照"构建内核镜像 → 装载并引导内核 → 建立内核栈 → 初始化运行环境 → 实现格式化输出 → 运行验证"的顺序展开。其中，内核构建过程与处理器启动后的执行过程需要区分：前者通过交叉编译、链接和镜像转换生成可供 QEMU 装载的文件；后者从机器复位开始，经由 OpenSBI 将执行权交给内核，并完成内核自身的初始化。

整体流程如下：

```text
C / 汇编源码
    ↓ 交叉编译与链接
bin/kernel（ELF）
    ↓ objcopy
bin/ucore.img（裸二进制镜像）
    ↓ QEMU 装载至 0x80200000
QEMU 模拟机器复位（0x1000）
    ↓
OpenSBI 固件（基址 0x80000000）
    ↓ 移交执行权
kern_entry（0x80200000）
    ↓ 设置内核栈
kern_init
    ↓ 清零 BSS
cprintf → console → SBI ecall → OpenSBI 控制台服务
    ↓
输出启动信息，进入无限循环
```

这一流程体现了最小内核的逐层构建思路：先使内核镜像能够被正确装载和执行，再建立运行 C 语言代码所需的基础条件，最后利用 OpenSBI 的服务验证内核的输出能力，为后续实验扩展更多操作系统功能奠定基础。

### 3.2 功能的逐步实现

#### （1）编译、链接并生成内核镜像

`Makefile` 组织 `libs/` 和 `kern/` 目录中的 C 语言、汇编源码编译，使用 RISC-V 交叉链接器和 `tools/kernel.ld` 生成 ELF 文件 `bin/kernel`，再通过 `objcopy --strip-all -O binary` 生成裸二进制镜像 `bin/ucore.img`。ELF 文件包含链接得到的段信息和符号信息，裸二进制镜像则只保留需要装入内存的字节内容。

**之所以首先完成这一步**，是因为后续一切分析与调试都以构建产物为前提：没有 `bin/kernel`，GDB 就无法获得符号信息；没有确定的链接地址，也无从讨论内核从哪里开始执行。

链接脚本通过 `ENTRY(kern_entry)` 指定内核入口，通过 `BASE_ADDRESS = 0x80200000` 确定内核链接基址；随后组织 `.text`、`.rodata`、`.data`、`.sdata` 和 `.bss` 等段，并利用 `ALIGN(0x1000)` 完成页对齐。这样既使内核的链接地址与装载地址保持一致，也为各类数据提供明确的地址布局。

#### （2）利用 QEMU 与 OpenSBI 装载并引导内核

`Makefile` 中的 `qemu` 目标通过 `-machine virt -nographic -bios default` 启动 RISC-V 虚拟机和默认 OpenSBI 固件，并将内核镜像装入 `0x80200000`（装载参数的环境差异见 2.3）。

在当前启动环境中，处理器先执行复位地址 `0x1000` 处的启动代码，进入基址为 `0x80000000` 的 OpenSBI 固件，随后由固件将控制权移交给内核入口 `0x80200000`。这里需要区分：QEMU 负责把镜像放入内存，OpenSBI 则负责固件阶段的初始化和向内核移交执行权。

**这一步紧接构建之后**，是因为只有先确认镜像能够被正确装载并取得控制权，后续对内核自身代码的分析才有意义。

#### （3）建立内核栈并进入 C 语言初始化函数

`kern/init/entry.S` 定义内核入口 `kern_entry`，并在 `.data` 段为启动栈预留空间。根据 `kern/mm/mmu.h` 和 `kern/mm/memlayout.h`，每页为 4096 字节，启动栈占两页，因此 `KSTACKSIZE = 8192` 字节（8 KiB）。

入口执行 `la sp, bootstacktop`，把预留栈空间的高地址端写入 RISC-V 栈指针 `sp`。因为栈向低地址增长，后续函数建立栈帧时可以向下使用这段内存。随后执行 `tail kern_init`，直接转入 C 语言编写的内核初始化函数。

**栈的建立必须排在调用任何 C 函数之前**：内核刚取得控制权时，`sp` 中残留的是固件留下的值，不属于内核，此时若直接调用 C 函数将破坏不属于自己的内存。这是本章节中顺序关系最严格的一处。

#### （4）完成内核最基本的运行环境初始化

`kern/init/init.c` 中的 `kern_init` 使用链接脚本提供的 `edata` 和 `end` 两个符号，执行 `memset(edata, 0, end - edata)`，清零 BSS 对应的内存区域，使未显式初始化的全局变量和静态变量具有符合 C 语言要求的初始值。之后函数调用 `cprintf` 输出启动信息，最后进入 `while (1)` 无限循环。函数被声明为 `__attribute__((noreturn))`，对应当前最小内核不返回入口代码的执行方式。

#### （5）利用 SBI 服务实现内核控制台输出

由于当前内核不能直接使用宿主操作系统提供的标准 C 库，它在项目内部实现格式化输出，并借助 OpenSBI 提供的控制台服务完成实际字符输出。其主要调用关系为：

```text
kern_init
    ↓
cprintf（kern/libs/stdio.c）
    ↓
vcprintf → vprintfmt
    ↓
cputch → cons_putc（kern/driver/console.c）
    ↓
sbi_console_putchar（libs/sbi.c）
    ↓
sbi_call → ecall → OpenSBI
```

其中，`vprintfmt` 解析格式字符串并通过回调逐字符输出；`cons_putc` 提供统一的控制台输出接口；`sbi_console_putchar` 使用 SBI 字符输出服务。`sbi_call` 将服务编号放入 `a7`（`x17`）寄存器，把字符参数放入 `a0`（`x10`）寄存器后执行 `ecall`，由 OpenSBI 完成底层输出。通过逐层封装，上层格式化输出逻辑不需要直接操作硬件寄存器。

**输出能力之所以放在最后实现**，是因为它是整条链路的"验收手段"：只有当一行启动信息真正出现在终端上，才能证明前面的构建、装载、栈初始化和运行环境准备全都正确。

#### （6）运行及验证启动结果

实际执行 `make qemu` 后，QEMU 成功显示 OpenSBI 启动信息，其中 `Firmware Base` 为 `0x80000000`，并输出内核启动提示。同时，使用 `riscv64-unknown-elf-nm` 检查构建得到的 `bin/kernel`，确认入口函数、初始化函数和启动栈的链接地址与源码分析一致。

以上验证说明当前工具链、镜像构建和模拟器启动环境能够正常使用，并为分析最小内核的执行流程提供了依据。

#### 1．构建与链接模块

`Makefile` 调用 RISC-V 交叉编译工具链，将 C 文件和汇编文件编译为目标文件，再通过链接器生成内核 ELF 文件 `bin/kernel`，并使用 `objcopy` 生成内核镜像。

链接脚本 `tools/kernel.ld` 指定目标架构、入口符号和内核基址，其中关键配置为：

```text
OUTPUT_ARCH(riscv)
ENTRY(kern_entry)
BASE_ADDRESS = 0x80200000
```

链接脚本还负责组织代码段、只读数据段、数据段和 BSS 区域，并设置对齐要求。`ENTRY(kern_entry)` 指定 ELF 入口符号，而本次调试进一步验证了 `kern_entry` 的实际地址为 `0x80200000`。

调试时加载带有符号信息的 ELF 文件，使 GDB 能够将机器地址对应到 `kern_entry`、`kern_init` 等函数及相关源码位置。

#### 2．汇编入口 `kern_entry`

`kern_entry` 是内核启动的汇编入口，其主要工作是设置启动栈并进入 C 初始化函数：

```asm
la sp, bootstacktop
tail kern_init
```

启动栈空间由汇编中的空间预留指示建立，`la` 指令负责将其栈顶地址写入 SP，不负责动态申请内存。RISC-V 栈向低地址增长，因此使用预留区域的高地址作为初始栈顶。

根据符号检查，本次构建的启动栈边界为：

```text
bootstack    = 0x80201000
bootstacktop = 0x80203000
```

两者相差 `0x2000`，即 8192 字节。图 5 通过寄存器和符号地址对照，验证了启动栈指针设置正确。

`tail kern_init` 将控制权转交给 C 初始化函数，不建立普通函数调用所需的新返回链接，与初始化函数不返回的设计一致。

#### 3．`kern_init` 与内存初始化

`kern_init` 主要完成以下操作：

```text
初始化需要清零的数据区域
    → 输出内核启动信息
    → 进入无限循环
```

其中，清零操作通过以下语句完成：

```c
memset(edata, 0, end - edata);
```

`edata` 和 `end` 是链接脚本提供的边界符号，代码通过两者之差确定清零长度。`memset` 使用实验工程自身的实现（`libs/string.c`），不依赖宿主系统的 C 标准库。

符号检查显示，本次构建中：

```text
edata = end = 0x80203008
```

因此，**该次构建的实际清零长度为零**。原因是当前最小内核没有任何未初始化的全局变量或静态变量，`.bss` 段为空。源码保留了通用的初始化流程，但不能据此描述为本次清除了一个非空的 BSS 区域。

之后，`kern_init` 调用 `cprintf` 输出：

```text
(THU.CST) os is loading ...
```

图 1 已经验证该输出出现。函数末尾的无限循环使最小内核保持运行，不返回到启动入口。

#### 4．格式化输出模块

格式化输出主要由 `cprintf`、`vcprintf` 和 `vprintfmt` 协作完成。

`cprintf` 接收格式字符串和可变参数，利用 `va_start` 初始化参数列表，调用 `vcprintf` 完成输出，再使用 `va_end` 清理。

`vcprintf` 设置字符计数器，将输出回调、计数器地址、格式字符串和参数列表交给 `vprintfmt`。

`vprintfmt` 负责解析格式字符串，将普通字符和格式化后的内容交给回调函数输出。数字转换由 `printnum` 等辅助函数完成。输出回调 `cputch` 则调用 `cons_putc` 输出字符，并更新计数。

这种设计将格式解析与底层字符输出分离：上层负责"输出什么"，下层负责"如何输出"。

#### 5．控制台输出与 SBI 调用

内核输出路径为：

```text
kern_init
    → cprintf
    → vcprintf
    → vprintfmt
    → cputch
    → cons_putc
    → sbi_console_putchar
    → sbi_call
    → ecall
    → OpenSBI 控制台服务
```

`cons_putc` 将字符转换为 `unsigned char` 后，交给 `sbi_console_putchar`。

`sbi_console_putchar` 使用传统 SBI 接口中的控制台输出服务编号（`SBI_CONSOLE_PUTCHAR = 1`），调用 `sbi_call`。后者通过内联汇编把服务编号放入 `x17`（`a7`）、参数放入 `x10`–`x12`（`a0`–`a2`），再执行 `ecall` 请求固件服务，返回值从 `x10`（`a0`）取回。

`ecall` 在 S 模式下执行会触发异常并陷入 M 模式，由 OpenSBI 提供服务。内核因此可以通过 SBI 完成控制台输出，而无需在这条输出路径中直接操作串口硬件。

图 1 中的启动提示验证了上述输出链能够正常工作。

#### 6．其他接口及实验范围

工程还包含单字符输出、字符串输出、输入接口和定时器服务等相关代码，但它们不能全部视为已经通过本实验验证。

`cputchar` 用于输出单个字符，`cputs` 用于输出字符串并追加换行。输入路径依赖 `cons_getc` 和相关 SBI 输入接口；原包中存在声明但未提供实现的输入函数。本次启动主路径未使用该功能，未使用代码在链接过程中被丢弃，因此最小内核仍能正常链接和运行。

`console.c` 中的部分初始化、中断函数为空实现。定时器封装（`sbi_set_timer`）也未在本次启动主路径中验证。因此，本实验确认的是最小内核启动、栈初始化和字符输出，不能据此声称已经实现完整的输入、中断或调度功能。

#### 7．QEMU、OpenSBI 与 GDB 的关系

| 模块 | 本实验中的作用 |
|---|---|
| QEMU | 模拟 RISC-V 硬件平台，加载固件与内核，提供远程调试接口 |
| 复位引导代码 | 准备启动参数，跳转到 OpenSBI |
| OpenSBI | 提供机器模式固件服务，并将控制权交给内核 |
| 内核 | 设置启动栈，执行初始化函数并输出启动信息 |
| GDB | 读取寄存器、反汇编、设置断点和控制单步执行 |

这些模块共同构成了从模拟硬件启动到内核执行的完整实验路径。

### 练习 1：理解内核启动中的程序入口操作

**负责人：** 2411292-张旭

> **题目：** 阅读 `kern/init/entry.S` 内容代码，结合操作系统内核启动流程，说明指令 `la sp, bootstacktop` 完成了什么操作，目的是什么？`tail kern_init` 完成了什么操作，目的是什么？

#### 1. 内核入口与启动栈的定义

`tools/kernel.ld` 中使用 `ENTRY(kern_entry)` 指定内核入口，链接基址为 `0x80200000`。`kern/init/entry.S` 的入口代码如下：

```asm
kern_entry:
    la sp, bootstacktop
    tail kern_init
```

启动栈由同一文件中的下列汇编定义：

```asm
.section .data
    .align PGSHIFT
    .global bootstack
bootstack:
    .space KSTACKSIZE
    .global bootstacktop
bootstacktop:
```

`mmu.h` 定义 `PGSIZE = 4096`、`PGSHIFT = 12`；`memlayout.h` 定义 `KSTACKPAGE = 2`、`KSTACKSIZE = KSTACKPAGE * PGSIZE`。因此，预留的启动栈大小为 `2 × 4096 = 8192` 字节，即 8 KiB。`bootstack` 指向这块区域的低地址边界，`bootstacktop` 指向高地址边界；`.align PGSHIFT` 将栈起点对齐到 4096 字节边界。

#### 2. `la sp, bootstacktop` 的作用和设计原因

`la` 是 Load Address 汇编伪指令，`sp` 是 RISC-V 的栈指针寄存器 `x2`。`la sp, bootstacktop` 将符号 `bootstacktop` 的**地址**装入 `sp`，而不是读取该地址处的数据，其语义可以表示为：

```text
sp ← address(bootstacktop)
```

RISC-V 的栈按照调用约定向低地址增长，因此启动时将 `sp` 设置到预留栈空间的高地址端。后续函数调用、保存寄存器或分配局部变量时，栈指针可向低地址移动，在 `[bootstack, bootstacktop)` 内使用内存。如果直接把 `sp` 设置成 `bootstack`，入栈操作就可能越过预留区域的低地址边界。

**这样设计的原因是**：内核刚获得控制权时，不能假定当前栈指针已经指向属于自身的有效栈空间（实测进入内核入口断点时 `sp = 0x80045e30`，仍是固件遗留值）。先设置 `sp` 才能为随后执行的 C 函数提供基本的栈运行环境。

#### 3. `tail kern_init` 的作用和设计原因

`tail` 是 RISC-V 的尾调用伪指令。`tail kern_init` 将执行权转移给函数 `kern_init`，并且不会像普通的 `call` 一样将新的返回地址写入 `ra` 寄存器。

在本实验中，`kern_entry` 只负责建立栈，不需要在 `kern_init` 执行结束后恢复运行。同时，`kern/init/init.c` 将 `kern_init` 声明为 `__attribute__((noreturn))`，函数完成 BSS 清零和启动信息输出后进入无限循环，不会返回。因此使用 `tail` 更符合入口阶段一次性交出控制权的目的，也避免了不必要的返回地址设置。实测反汇编显示该尾调用对应单条 `j 0x8020000a` 指令，印证了"不建立返回链接"这一点。

#### 4. 构建产物中的符号地址验证

在 `code` 目录中执行：

```bash
riscv64-unknown-elf-nm -n bin/kernel | grep -E ' (kern_entry|kern_init|bootstack|bootstacktop)$'
```

实际输出为：

```text
0000000080200000 T kern_entry
000000008020000a T kern_init
0000000080201000 D bootstack
0000000080203000 D bootstacktop
```

该结果表明 `kern_entry` 位于 `0x80200000`，`kern_init` 位于 `0x8020000a`。当前构建的启动栈范围是 `[0x80201000, 0x80203000)`，大小为 `0x2000 = 8192` 字节。执行 `la sp, bootstacktop` 后，初始 `sp` 指向 `0x80203000`。这两个栈边界地址由本次链接结果确定；如果前面的代码段或数据段大小变化，实际地址也可能发生变化。

该结论与练习 2 中 GDB 实测的 `sp = 0x80203000` 完全一致，两种独立手段相互印证。

#### 5. 练习结论

`la sp, bootstacktop` 和 `tail kern_init` 共同完成内核入口的两项关键操作：前者为内核建立可用的栈空间，后者将执行权交给不会返回的 C 语言初始化函数。两条指令按此顺序执行，使最小内核能够从早期汇编入口过渡到后续的 C 语言初始化过程。

#### 2．观察复位入口及最初六条指令

以暂停模式启动 QEMU，再使用 GDB 加载 `bin/kernel` 并连接远程调试接口。本次截图使用启动脚本建立连接，调试端口为 `127.0.0.1:1235`。

读取程序计数器并查看指令：

```gdb

x/6i $pc
```

结果显示，CPU 初始停在 `0x1000`，该地址处的前六条指令如下：

```asm
0x1000: auipc t0,0x0
0x1004: addi  a2,t0,40
0x1008: csrr  a0,mhartid
0x100c: ld    a1,32(t0)
0x1010: ld    t0,24(t0)
0x1014: jr    t0
```

![图2 复位入口与最初六条指令](images/figure2.png)

*图 2　初始 PC 为 `0x1000`，GDB 显示复位引导代码。*

这些指令位于本次 QEMU virt 平台的复位引导区域（MROM），其作用是准备启动参数并跳转到固件入口。各条指令的具体作用如下：

| 地址 | 指令 | 作用 |
|---|---|---|
| `0x1000` | `auipc t0,0x0` | 将当前 PC 写入 `t0`，得到基址 `0x1000` |
| `0x1004` | `addi a2,t0,40` | 设置 `a2=0x1028`，传递动态固件信息结构的地址 |
| `0x1008` | `csrr a0,mhartid` | 读取当前硬件线程编号，作为启动参数 |
| `0x100c` | `ld a1,32(t0)` | 从 `0x1020` 读取设备树地址，保存到 `a1` |
| `0x1010` | `ld t0,24(t0)` | 从 `0x1018` 读取固件入口，保存到 `t0` |
| `0x1014` | `jr t0` | 跳转到 `t0` 指定的入口，开始执行 OpenSBI |

**练习 2 的第一问答案：** RISC-V 硬件加电后最初执行的指令位于 **`0x1000`**。这是本次 QEMU `virt` 平台设定的复位地址，不能将其视为所有 RISC-V 设备通用的固定地址。

**第二问答案：** 这六条指令完成的是**启动参数准备与固件跳转**，具体包括三件事 —— 其一，通过 `auipc` 取得自身所在的基址，使后续访问可以采用相对寻址；其二，按 RISC-V 启动约定准备三个参数：`a0` 存放当前 hart 编号、`a1` 存放设备树（FDT）地址、`a2` 存放动态固件信息结构地址；其三，从固定偏移处读出 OpenSBI 的入口地址并跳转过去。它们本身不做任何硬件初始化，只扮演"交接棒"的角色。

#### 5．验证启动栈初始化

继续执行：


结果为：


![图5 启动栈初始化](images/figure5.png)

*图 5　执行两条机器指令后，SP 与 `bootstacktop` 地址一致，启动栈初始化完成。*

结合图 4 中的反汇编，内核入口对应的机器指令为：

```asm

0x80200004: mv    sp,sp
0x80200008: j     0x8020000a
```

汇编伪指令 `la sp, bootstacktop` 在本次构建中展开为前两条机器指令。第一条设置 SP，第二条是零偏移调整，在反汇编中显示为 `mv sp,sp`。执行 `si 2` 后，PC 停在 `0x80200008`，SP 已等于 `bootstacktop`，说明内核建立了自己的启动栈。

这里需要区分"执行一条汇编源码中的伪指令"和"执行一条机器指令"：图 5 记录的是执行两条机器指令后的状态，而第一条机器指令执行后的中间位置为 `0x80200004`。

GDB 在 SP 后显示的 `<SBI_CONSOLE_PUTCHAR>` 属于地址的符号标注，不表示正在调用该服务。通过 `p/x &bootstacktop` 可直接确认，当前 SP 就是内核启动栈顶地址。

#### 6．关于观察点的说明

断点用于观察程序是否执行到指定位置；数据观察点用于监视某个位置的数据是否变化，两者用途不同。

本次内核由 QEMU 在 CPU 开始运行之前加载到内存。因此，在连接 GDB 后设置：

```gdb
watch *(unsigned int *)0x80200000
```

不能保证捕获此前已经完成的加载动作，也不能据此判断是否执行到了内核入口。本实验采用内核入口断点和单步执行验证控制流，没有将未实际记录的观察点行为作为实验结果。

#### 7．练习 2 结论

| 观察阶段 | PC | 关键结果 |
|---|---|---|
| 初次连接 GDB | `0x1000` | 显示复位引导代码 |
| 执行六条复位指令后 | `0x80000000` | 进入 OpenSBI，启动参数已准备好 |
| 内核入口断点命中 | `0x80200000` | 进入 `kern_entry`，尚未执行栈初始化 |
| 执行两条内核机器指令后 | `0x80200008` | `sp = bootstacktop = 0x80203000` |
| 后续跳转目标 | `0x8020000a` | `kern_init` 的入口 |

实验验证了从复位代码、经过 OpenSBI、进入内核并完成启动栈初始化的全过程。启动输出则进一步证明，内核能够执行到 C 初始化函数中的控制台输出路径。

## 六、实验总结与收获

### 6.1 对操作系统的理解

#### 一、本实验的重要知识点及其与 OS 原理的对应

##### 1. 特权级与 `ecall`：一次完整的"系统调用"

**实验中的含义.** RISC-V 定义了 M（机器态）、S（监管态）、U（用户态）三个特权级。OpenSBI 运行在 M 态，我们的内核运行在 S 态。内核想输出一个字符，不能直接去碰串口的硬件寄存器，而必须把功能号 `SBI_CONSOLE_PUTCHAR = 1` 放进 `a7`、参数放进 `a0`–`a2`，然后执行一条 `ecall` 主动触发异常，陷入 M 态由固件完成实际操作，结果经 `a0` 返回（`libs/sbi.c` 的 `sbi_call`）。

**OS 原理中的对应.** 处理器的双模式保护与系统调用机制：应用程序无权执行特权操作，只能通过一条专门指令陷入内核；陷入点是受控的单一入口，参数按寄存器约定传递，内核依据功能号分发到具体服务例程。

**关系.** 二者是同构的。都遵循"低特权级无法直接完成某事 → 用一条专门指令主动陷入高特权级 → 高特权级按约定编号分发服务 → 带结果返回"这同一套模型。lab1 里的 SBI 调用就是一次货真价实的系统调用，只不过调用方是内核、被调用方是固件。

**差异.** 三点不同。其一，方向相反：原理课讲的是 U→S，本实验是 S→M。其二，被调用方不同：不是内核而是固件。其三，也是最关键的 —— **本实验只实现了调用方这一半**。我们写了发起 `ecall` 的代码，却没有写接收、保存现场、分发、返回的代码，那部分由 OpenSBI 完成。所以 lab1 只能让我们理解系统调用的"客户端"，"服务端"要等到自己实现 trap 处理时才会真正接触。

##### 2. 启动流程：固件到内核的三级接力

**实验中的含义.** 用 GDB 实测到的完整链条是：CPU 复位后 `pc = 0x1000`，执行 MROM 中写死的六条指令（准备 hart 编号、设备树地址等启动参数，并跳转）；随后进入 `0x80000000` 的 OpenSBI，由它完成硬件初始化；最后跳转到 `0x80200000`，即链接脚本指定的内核入口 `kern_entry`。

**OS 原理中的对应.** 系统引导（bootstrapping）：加电 → 固化在 ROM 中的固件自检并初始化硬件 → 从外存读入引导程序 → 引导程序把内核装入内存并移交控制权。

**关系.** 三级结构一一对应：MROM 对应 ROM 固件，OpenSBI 对应 BIOS/UEFI 加引导程序，`kern_entry` 对应内核入口。都在解决同一个问题 —— CPU 复位后只能执行固定地址上的极少量代码，如何逐级放大能力直到内核就位。

**差异.** 最值得注意的一点：x86 上的引导程序（如 GRUB）把控制权交给内核后基本退场，而 **OpenSBI 移交控制权后仍常驻 M 态**，持续为内核提供运行时服务。它既是引导程序，又是运行时的服务提供者。这种"引导程序不退场"的形态，在传统教材的引导程序概念里是没有的。

##### 3. SBI：一个跨特权级的硬件抽象层

**实验中的含义.** 输出功能被封装成五层：`sbi_call`（内联汇编发 `ecall`）→ `sbi_console_putchar`（固定功能号）→ `cons_putc`（`kern/driver/console.c`）→ `cputch`/`cputs`（`kern/libs/stdio.c`）→ `cprintf`（配合 `libs/printfmt.c` 做格式化）。最上层的 `cprintf` 完全不知道底下是 `ecall` 还是别的什么。

**OS 原理中的对应.** 硬件抽象层（HAL），以及机器相关代码与机器无关代码的分离 —— 把硬件差异收敛到一组接口之下，使内核的大部分代码可移植。

**关系.** 都是用接口挡住硬件差异，再逐层向上封装出好用的抽象。

**差异.** 教材里的 HAL 通常是**内核内部的软件分层**：同一特权级、同一个二进制文件里的普通函数调用。而 SBI 是**跨特权级、跨二进制的接口规范**（Supervisor Binary Interface），由一个独立的程序（固件）实现，进入方式是一条指令而不是函数调用。换句话说，SBI 更接近"ABI 规范"，而不是"代码分层"。

##### 4. 链接脚本与内存布局：没有 MMU 时，地址必须被写死

**实验中的含义.** `tools/kernel.ld` 里 `BASE_ADDRESS = 0x80200000` 是硬编码的，`ENTRY(kern_entry)` 指定入口符号，并且 `.text` 段中强制把 `*(.text.kern_entry)` 排在最前，以保证入口代码恰好落在镜像起始、也就是 `0x80200000` 处。本实验中**链接地址 = 加载地址 = 物理地址**，三者完全相等。另外，`.bss` 段在镜像中不占体积（只记录大小和位置），所以 `kern_init` 做的第一件事就是 `memset(edata, 0, end - edata)` 手工清零，其中 `edata`、`end` 两个符号由链接脚本的 `PROVIDE` 定义。

**OS 原理中的对应.** 程序的地址空间与存储分配：代码段、数据段、BSS、栈、堆的划分；以及装入方式的分类 —— 绝对装入、可重定位装入、运行时动态装入。

**关系.** 段的划分概念完全一致。`kernel.ld` 正是"绝对装入"的极端案例：编译链接期就把运行地址彻底定死，运行时不做任何重定位。

**差异.** 应用程序有操作系统和 MMU 替它做重定位与隔离；内核自己没人伺候，只能和固件事先约定一个物理地址，写进链接脚本。lab1 全程没有虚拟地址、没有页表，这恰好从反面凸显了分页机制要解决什么问题（重定位、隔离、超额分配）。还有一处细节差异：应用程序的 `.bss` 清零由 C 运行时启动代码（crt0）完成，而内核没有 crt0，只能自己动手。

##### 5. 内核栈：C 语言运行环境的前提

**实验中的含义.** `entry.S` 的第一条指令 `la sp, bootstacktop` 把 `sp` 指向 `.data` 段中预留的一块空间的高端。这块空间大小为 `KSTACKSIZE = KSTACKPAGE × PGSIZE = 2 × 4096 = 8 KB`，GDB 实测执行后 `sp = 0x80203000`。在此之前，`sp` 里残留的是固件留下的值（实测为 `0x80045e30`），不属于内核，此时调用任何 C 函数都不安全 —— 这正是必须先设栈、再 `tail kern_init` 的原因。栈从高地址向低地址增长，所以 `sp` 指向的是 `bootstacktop` 而非 `bootstack`。

**OS 原理中的对应.** 内核栈：每个进程/线程都有自己的内核栈，用于保存函数调用链、局部变量，以及陷入内核时的现场；上下文切换的本质之一就是切换栈指针。

**关系.** 都在回答同一个问题 —— 函数调用赖以生存的运行时栈从哪里来。lab1 建立的是整个内核的第一个、也是唯一一个栈。

**差异.** lab1 的栈是**全局唯一、静态分配、编译期确定大小、只有一条控制流使用**；原理中的内核栈是每进程一个、随进程创建与销毁而动态分配。lab1 没有上下文切换，`sp` 一旦设好就不再更换，因此也不存在"切栈"这件事。

##### 6. 自举困境：为什么要自己写 `cprintf`

**实验中的含义.** 内核里不能 `#include` 标准库的 `<stdio.h>`。因为 glibc 的 `printf` 最终要通过系统调用把数据交给操作系统，而我们正在写的就是操作系统 —— 这构成了循环依赖。于是 `libs/string.c` 自己实现了 `memset`，`kern/libs/stdio.c` 与 `libs/printfmt.c` 自己实现了格式化输出。工具链名字 `riscv64-unknown-elf-gcc` 中的 `elf`（而非 `linux-gnu`）后缀，正表示它面向**没有操作系统的裸机目标**。

**OS 原理中的对应.** 操作系统为应用程序提供运行环境：系统调用接口、标准库支持、程序的装入启动与退出。

**关系.** 这是同一件事的两面。原理课从"操作系统提供了什么"的角度讲；lab1 则把我们放到"操作系统还不存在"的位置上，让我们亲手体会缺了这些会怎样。

**差异.** 原理课默认运行环境已经就位；lab1 是自举视角 —— 内核是唯一一个不能依赖操作系统的程序。这个差异不只是观念上的，它直接决定了编译选项（不链接标准库）、工具链选择和代码写法。

##### 7. ELF 与裸二进制：装入器工作的前移

**实验中的含义.** `make` 先链接出 `bin/kernel`，这是一个 ELF 文件（本次实测 48744 字节），含符号表和节头信息，GDB 正是靠它才能识别出 `kern_entry`、`kern_init` 这些符号并在源码行上下断点。随后 `riscv64-unknown-elf-objcopy --strip-all -O binary` 把它剥成 `bin/ucore.img`（12296 字节），只剩下需要装进内存的纯字节流。前者给调试器看，后者给机器装入。

**OS 原理中的对应.** 可执行文件格式与装入过程：装入器读取文件头，按各段的地址信息把内容搬进内存，建立进程映像，然后跳转到入口点。

**关系.** 都在区分"文件形态"与"内存映像"这两个概念。`objcopy` 所做的事，本质上是把装入器的工作提前到了编译期完成。

**差异.** 应用程序由操作系统的装入器在运行时解析 ELF 并建立映像；内核启动时根本没有装入器可用，所以干脆预先剥成裸二进制，由固件直接搬到约定地址了事。需要澄清的是，QEMU 的 `-kernel` 参数两种文件都能接受（实测 ELF 与裸二进制均可正常启动，OpenSBI 报告的 `Next Address` 都是 `0x80200000`），因为 QEMU 自己就能解析 ELF 程序头并按段装入 —— 这相当于模拟器替我们扮演了装入器。但在真实硬件上没有人提供这项服务，所以内核镜像最终仍要以裸二进制形式交付，`objcopy` 这一步正是为此存在。

|---|---|---|---|

### 6.2 AI 协作开发的经验

**一、把"不要改代码"写进提示词，理解阶段才不会失控。** 在源码分析阶段，提示词中明确加入"你先不要修改任何文件""先只分析，不要改代码"这样的约束，AI 才会老老实实只做只读分析。否则它很容易一边解释一边"顺手"改动源码，导致后续分不清哪些是原始代码、哪些是 AI 的改动。本实验两个分析类模块都采用了这一约束，实际效果良好。

**二、AI 的结论必须用工具实测复核，不能直接写进报告。** 这是本次最重要的一条经验。例如 AI 指出 `tail kern_init` 在反汇编中对应 `j kern_init`，我们没有直接采信，而是用 `riscv64-unknown-elf-nm` 核对符号地址、用 GDB 单步确认反汇编，两者一致后才写入报告。又如 AI 分析 `memset(edata, 0, end - edata)` 时描述的是"清零 BSS 区域"，但实测 `edata = end = 0x80203008`，本次构建的清零长度其实为零 —— 这种只有动手查符号表才能发现的细节，AI 基于源码的静态分析给不出来。

**三、要区分"AI 说的"和"我们验证过的"。** 在记录迭代过程时，我们刻意避免把尚未执行的步骤写成已验证结果。例如第一次迭代时并未进行 GDB 跟踪，报告中就明确注明"本次未进行 GDB 启动过程跟踪"，而不是把 AI 推演出的启动流程当作实测结论。这个习惯让报告中的每个地址、每个寄存器值都有据可查。

**四、环境差异是 AI 最容易误导人的地方。** 本次三位成员的 QEMU 版本不同，导致同一份 `Makefile` 在不同机器上表现不一致。AI 依据指导书给出的说明默认 `-device loader` 可用，但在新版 QEMU 上这是错的。最终是通过对比 OpenSBI 实际输出的 `Domain0 Next Address` 字段才定位到根因（`fw_jump` 与 `fw_dynamic` 两种固件形态的差别）。这说明：**凡是涉及具体版本行为的结论，必须以本机实测输出为准**，AI 的训练数据和课程文档都可能滞后。

**五、提示词要给足"最小可信上下文"。** 按照 lab0.5 的四段式规范，`[RELY]` 部分提供的宏定义和数据结构必须与工程代码完全一致。本实验中询问栈大小时，我们直接点名让 AI 结合 `entry.S`、`memlayout.h`、`mmu.h` 和链接脚本来分析，而不是泛泛地问"栈有多大"，得到的回答才准确到了 `KSTACKPAGE = 2`、`PGSIZE = 4096`、总计 8192 字节这一层。

**六、AI 擅长梳理调用链，不擅长判断边界条件。** 像 `cprintf → vcprintf → vprintfmt → cputch → cons_putc → sbi_console_putchar → sbi_call → ecall` 这样的多层调用关系，AI 能很快理清并画出完整链路，这是它的强项。但诸如"哪些函数只是声明而没有实现""哪些空函数在本次启动路径上根本没被调用""未使用的代码在链接时会被丢弃"这类涉及实际构建行为的判断，仍然需要人工查阅符号表和链接结果来确认。
